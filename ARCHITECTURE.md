## 1. Architecture goal

Define a production architecture that preserves the approved local-processing promise, keeps PDF libraries replaceable, makes coordinate correctness testable, and supports incremental delivery without coupling the editor interface to a particular PDF implementation.

This document specifies contracts and invariants. Phase 4 will test risky assumptions before production scaffolding.

## 2. Architectural drivers

The architecture is governed, in order, by:

1. Document confidentiality: files remain local unless a future user explicitly chooses a separate cloud workflow.
2. Document integrity: the original is immutable and invalid exports are blocked.
3. Coordinate correctness across zoom, crop boxes, rotation, and mixed page sizes.
4. Honest support boundaries for existing text, encryption, forms, and signatures.
5. Replaceable rendering, export, persistence, and validation implementations.
6. Responsive behavior under bounded resource use.
7. Reversible editing and recoverable sessions.
8. Accessible interaction independent of visual canvas pixels.
9. Deterministic exports and reproducible tests.

## 3. System context

```text
                         Same-origin static assets
                                  |
                                  v
User file -> Browser editor -> PDF renderer worker
                |       |
                |       +------> Local recovery store
                |
                +--------------> PDF export worker
                                      |
                                      v
                              Local validation
                                      |
                                      v
                              Browser download
```

There is no document API in Version 1. The hosting service delivers static application assets and security headers. It does not receive PDF bytes, filenames, form values, annotations, signatures, or generated output.

## 4. Architectural boundaries

### 4.1 Presentation

Responsibilities:

- Editor layout, toolbars, panels, dialogs, and accessible controls
- Pointer, keyboard, touch, and assistive-technology input
- Rendering view models and user-visible progress/errors
- Dispatching domain commands

Restrictions:

- Must not import PDF.js or `pdf-lib`.
- Must not store PDF library objects.
- Must not perform PDF coordinate conversion directly.
- Must not write recovery records directly.

### 4.2 Editor application

Responsibilities:

- Open/close lifecycle
- Command dispatch
- Selection and tool state
- Export orchestration
- Recovery orchestration
- Capability and warning decisions

It depends only on domain types and ports.

### 4.3 Domain

Responsibilities:

- Document graph
- Page geometry
- Edit objects
- Commands and transactions
- Invariants and validation
- Capability outcomes

Restrictions:

- Pure TypeScript with no React, DOM, canvas, IndexedDB, PDF.js, or `pdf-lib` imports.
- All state transitions are deterministic for a given state and command.

### 4.4 PDF infrastructure

Responsibilities:

- Rendering adapter
- Export adapter
- Form inspection
- Signature/encryption inspection where supported
- Generated-file validation
- Library-specific error translation

PDF library types terminate at this boundary.

### 4.5 Local persistence

Responsibilities:

- Recovery manifests
- Original/source blobs
- User-added asset blobs
- Schema migration
- Expiry and deletion
- Quota handling

The editor depends on a `RecoveryStore` port, not IndexedDB directly.

## 6. Domain identifiers and primitives

Identifiers are opaque branded strings generated by one tested ID service:

```ts
type DocumentId = Brand<string, "DocumentId">;
type SourceId = Brand<string, "SourceId">;
type PageId = Brand<string, "PageId">;
type ObjectId = Brand<string, "ObjectId">;
type AssetId = Brand<string, "AssetId">;
type FieldId = Brand<string, "FieldId">;
type TransactionId = Brand<string, "TransactionId">;
```

Numeric primitives:

```ts
type PdfPoint = Brand<number, "PdfPoint">;
type Degrees = 0 | 90 | 180 | 270;
type UnitInterval = Brand<number, "UnitInterval">; // inclusive 0..1
```

Runtime parsers validate persisted or worker-supplied values. TypeScript types alone are not trusted at I/O boundaries.

## 7. Document aggregate

```ts
interface EditorDocument {
  schemaVersion: number;
  id: DocumentId;
  revision: number;
  createdAt: string;
  updatedAt: string;
  sources: Record<SourceId, SourceDocument>;
  pages: PageInstance[];
  objects: Record<ObjectId, EditObject>;
  objectOrderByPage: Record<PageId, ObjectId[]>;
  formValues: Record<FieldId, SupportedFormValue>;
  assets: Record<AssetId, AssetDescriptor>;
  warnings: DocumentWarning[];
}
```

Invariants:

- `revision` increases after each committed transaction.
- Source bytes are not contained in domain state.
- Every page references an existing source page.
- Every object references an existing page.
- Each object appears exactly once in its page's z-order.
- Asset-backed objects reference an existing asset.
- Deleted pages have no active objects or form values.
- Domain state is serializable without functions, classes, blobs, DOM nodes, or library objects.

## 8. Source documents and page graph

```ts
interface SourceDocument {
  id: SourceId;
  fingerprint: string;
  originalName: string;
  byteLength: number;
  pageCount: number;
  encryption: "none" | "unsupported" | "unknown";
  signatureState: "none" | "present" | "unknown";
  capabilities: DocumentCapabilities;
}

interface PageInstance {
  id: PageId;
  sourceId: SourceId;
  sourcePageIndex: number;
  userRotation: Degrees;
  geometry: SourcePageGeometry;
}
```

Pages form an ordered graph of references rather than copied PDF bytes. Reordering changes the `pages` array. Duplication creates a new `PageId` pointing to the same source page. Adding another PDF creates a new source and page instances.

`originalName` is treated as private document data. It may appear in the local interface and recovery record but never in telemetry or error reporting.

## 9. Canonical page coordinate system

### 9.1 Definition

Every edit object is stored in **canonical page space**:

- Unit: PDF points, where 72 points equal one inch.
- Origin: top-left of the displayed crop box.
- Positive X: right.
- Positive Y: down.
- Zoom: always 1.
- Device-pixel ratio: absent.
- Dimensions: effective displayed crop-box width and height after intrinsic plus user rotation.

Canonical page space is designed for editor semantics. It is not raw PDF user space and not a browser pixel coordinate system.

### 9.2 Geometry record

```ts
interface SourcePageGeometry {
  mediaBox: PdfBox;
  cropBox: PdfBox;
  intrinsicRotation: Degrees;
}

interface DerivedPageGeometry {
  effectiveRotation: Degrees;
  canonicalWidth: PdfPoint;
  canonicalHeight: PdfPoint;
  pdfToCanonical: AffineMatrix;
  canonicalToPdf: AffineMatrix;
}

interface PdfBox {
  xMin: PdfPoint;
  yMin: PdfPoint;
  xMax: PdfPoint;
  yMax: PdfPoint;
}

type AffineMatrix = readonly [number, number, number, number, number, number];
```

Derived geometry is computed, not persisted as authoritative state. The inverse matrix must be verified within a documented floating-point tolerance.

Matrix convention:

```text
x' = a*x + c*y + e
y' = b*x + d*y + f

AffineMatrix = [a, b, c, d, e, f]
```

Matrices compose right-to-left: `compose(A, B)` means apply `B` first, then `A`. One shared domain geometry module owns creation, composition, inversion, and application. Adapters may translate this representation at their boundary but may not introduce a second authoritative convention.

### 9.3 Transform chain

```text
PDF user space
   ⇄ crop translation and effective rotation
Canonical page space
   ⇄ zoom and viewport translation
CSS viewport space
   ⇄ device-pixel ratio
Canvas backing space
```

No tool may skip levels or embed zoom/device-pixel values in document state.

### 9.4 Pointer conversion

1. Read the pointer position relative to the page viewport's CSS border box.
2. Undo CSS viewport translation.
3. Divide by current zoom.
4. Produce canonical page coordinates.
5. Clamp or reject according to the active tool.
6. Store canonical values without integer rounding.

### 9.5 Rotation behavior

Changing `userRotation` is a transaction. Positive page rotation is clockwise. Existing objects are transformed so they rotate with the page and preserve their relationship to its content. The transaction records the previous object geometry and page rotation, allowing exact undo without attempting a second floating-point inverse.

For an old canonical page of width `W` and height `H`, point transforms are:

```text
Clockwise 90:  (x, y) -> (H - y, x)       new size H × W
Clockwise 180: (x, y) -> (W - x, H - y)   new size W × H
Clockwise 270: (x, y) -> (y, W - x)       new size H × W
```

Axis-aligned frame transforms are edge-based:

```text
Frame = (x, y, width, height)

Clockwise 90:
  (H - (y + height), x, height, width)

Clockwise 180:
  (W - (x + width), H - (y + height), width, height)

Clockwise 270:
  (y, W - (x + width), height, width)
```

Every ink vertex, line endpoint, and shape control point uses the point transform. Object-local rotation is increased by the clockwise page-rotation delta and normalized to `[0, 360)`. Applying four 90-degree page-rotation transactions followed by undo must restore the exact pre-transaction values from history.

### 9.6 Coordinate invariants

- View zoom never changes stored geometry.
- Device-pixel ratio never changes stored geometry.
- Forward then inverse transformation returns the starting point within tolerance.
- Export uses `canonicalToPdf`; it never derives coordinates from current DOM measurements.
- Text baseline and bounding-box semantics are explicit and tested separately.
- Crop-box offsets are preserved even when the media-box origin is not `(0, 0)`.
- A page-rotation transaction transforms every object on that page atomically.
- Matrices containing non-finite values or an effectively zero determinant are rejected.

### 9.7 Required coordinate golden cases

Before the coordinate module is accepted, tests must include:

- US Letter portrait with zero-origin media and crop boxes
- A4 landscape
- Non-zero and negative media-box origins
- Crop box smaller than and offset within the media box
- Intrinsic rotations of 0, 90, 180, and 270 degrees
- Each intrinsic rotation combined with each user rotation
- Points at all four crop-box corners and center
- Frames touching each edge
- Fractional coordinates and dimensions
- Forward/inverse round trips
- Four successive clockwise rotations
- Rotation followed by undo and redo

## 10. Edit object model

All objects share:

```ts
interface EditObjectBase {
  id: ObjectId;
  pageId: PageId;
  kind: EditObjectKind;
  frame: CanonicalFrame;
  rotation: number;
  opacity: UnitInterval;
  locked: boolean;
  createdAtRevision: number;
}

interface CanonicalFrame {
  x: PdfPoint;
  y: PdfPoint;
  width: PdfPoint;
  height: PdfPoint;
}
```

Version 1 variants:

- `TextObject`
- `WhiteoutObject`
- `ImageObject`
- `SignatureObject`
- `RectangleObject`
- `EllipseObject`
- `LineObject`
- `CheckmarkObject`
- `HighlightObject`
- `InkObject`

Object-specific data is a discriminated union. Examples:

```ts
interface TextObject extends EditObjectBase {
  kind: "text";
  text: string;
  font: FontReference;
  fontSize: PdfPoint;
  color: RgbaColor;
  horizontalAlignment: "left" | "center" | "right";
  lineHeight: number;
}

interface InkObject extends EditObjectBase {
  kind: "ink";
  paths: CanonicalPoint[][];
  stroke: RgbaColor;
  strokeWidth: PdfPoint;
}
```

Limits on text length, object count, image dimensions, ink points, and asset bytes are enforced at command validation and rechecked at export.

## 11. Assets

Images and drawn-signature rasters are stored in an `AssetRepository`, separate from domain state.

```ts
interface AssetDescriptor {
  id: AssetId;
  mediaType: "image/png" | "image/jpeg";
  byteLength: number;
  pixelWidth: number;
  pixelHeight: number;
  sha256: string;
}
```

Rules:

- Decode images before acceptance to verify type and dimensions.
- Ignore filename extensions as evidence of type.
- Strip unnecessary metadata when producing derived signature assets.
- Deduplicate identical assets by digest within a document.
- Object deletion does not remove an asset until no object or history entry references it.
- Asset garbage collection runs after history compaction and before recovery commits.

## 12. Form model

Forms are not represented as arbitrary edit objects.

```ts
interface SupportedFieldDescriptor {
  id: FieldId;
  sourceId: SourceId;
  sourcePageIndex: number;
  qualifiedName: string;
  kind: "text" | "checkbox" | "radio" | "dropdown";
  readOnly: boolean;
  required: boolean;
  options?: string[];
}
```

The PDF adapter maps supported fields into descriptors. Domain commands update values only when the descriptor and value type agree. Unsupported fields remain visible in rendering but are not presented as editable.

XFA is detected where possible and reported as unsupported.

## 13. Commands, transactions, and history

### 13.1 Command contract

```ts
interface EditorCommand<TPayload> {
  type: string;
  payload: TPayload;
}

interface CommandResult {
  next: EditorDocument;
  effects: DomainEffect[];
  change: ReversibleChangeSet;
}
```

Commands express user intent, including:

- Add, update, move, resize, rotate, duplicate, reorder, and delete object
- Add, reorder, rotate, duplicate, and delete page
- Set supported form value
- Add/remove asset reference

### 13.2 Transaction rules

- One user-visible action commits one transaction.
- Multi-object operations are atomic.
- Pointer movement previews are ephemeral and do not create history entries.
- Pointer release commits the final gesture as one transaction.
- Text typing is coalesced using explicit focus/session boundaries, not arbitrary timing alone.
- A failed command changes no domain state.
- Each transaction carries an ID, base revision, resulting revision, description key, and reversible change set.

### 13.3 Undo and redo

History uses reversible domain change sets, not complete PDF byte snapshots.

```ts
interface HistoryState {
  past: CommittedTransaction[];
  future: CommittedTransaction[];
  limit: number;
}
```

Rules:

- A new transaction clears the redo stack.
- Undo applies the inverse change set as an atomic state transition.
- Redo applies the forward change set.
- Undo/redo do not reuse mutable object references.
- History has bounded entries and estimated memory.
- Compaction never removes assets still referenced by recoverable history.
- Page deletion can be undone because its page, object, z-order, and form changes are one transaction.

## 14. Ephemeral UI state

The following is not part of the document aggregate:

- Active tool
- Selection
- Hover state
- Open panels/dialogs
- Current zoom
- Scroll position
- Render cache
- In-progress pointer preview
- Export progress
- Transient errors

Some view preferences may be persisted separately, but they never affect exported document meaning.

## 16. Worker architecture

### 16.1 Worker roles

- **Render worker:** PDF.js parsing, inspection, page rendering, and thumbnails.
- **Export worker:** source loading, deterministic export operations, hashing where needed, and generated-byte production.
- **Validation worker:** fresh parsing and changed-page smoke renders. It must not reuse the exporter parser state.

The spike may combine roles for experimentation, but production boundaries remain separate unless measurements justify an approved revision.

### 16.2 Protocol envelope

```ts
interface WorkerRequest<T> {
  protocolVersion: number;
  requestId: string;
  documentId: DocumentId;
  documentRevision?: number;
  operation: string;
  payload: T;
}

interface WorkerResponse<T> {
  protocolVersion: number;
  requestId: string;
  ok: boolean;
  result?: T;
  error?: WorkerError;
}
```

Rules:

- Runtime-validate every message.
- Reject unknown protocol versions and operations.
- Never include filenames, document text, form values, or signature data in generic errors.
- Support cancellation or generation invalidation for stale render jobs.
- Bound queued work and concurrent renders.
- Terminate workers on document close or unrecoverable protocol failure.
- Worker asset URLs are same-origin and CSP-constrained.

### 16.3 Byte ownership

The authoritative original is a local `Blob` held by a source repository. Workers request an `ArrayBuffer` when necessary. Transfer ownership is explicit; a transferred buffer must not be reused by the sender.

The spike must measure whether repeated `Blob.arrayBuffer()` calls and parser copies fit memory targets. Optimization may introduce a dedicated byte broker, but shared memory is not assumed.

## 17. Rendering pipeline

1. User selects a local file.
2. Application performs basic name/size checks without trusting the extension.
3. Source repository accepts the local blob and computes a digest.
4. Render adapter inspects bytes for parseability, pages, geometry, encryption, forms, and signatures.
5. Application creates the initial document aggregate only after successful inspection.
6. Viewport requests visible pages plus bounded overscan.
7. Render worker produces base page bitmaps/canvases.
8. Presentation renders edit objects in a separate interactive overlay using canonical-to-viewport transforms.
9. Zoom rerenders/repositions the view but does not mutate the document.
10. Offscreen page resources are disposed according to a bounded cache policy.

The base PDF canvas is not modified during editing.

## 18. Export snapshot

Export never reads live mutable UI state. The application creates:

```ts
interface ExportSnapshot {
  documentId: DocumentId;
  revision: number;
  sources: ExportSourceReference[];
  pages: ExportPage[];
  objectsByPage: Record<PageId, readonly EditObject[]>;
  formValues: Record<FieldId, SupportedFormValue>;
  assets: readonly ExportAssetReference[];
  exportOptions: ExportOptions;
}
```

The snapshot is deeply immutable and runtime-validated before crossing the worker boundary.

If the user edits after export starts, the job continues against its captured revision. The interface states which revision finished and does not mark newer changes as exported.

## 19. Deterministic export pipeline

1. Verify source and asset availability.
2. Recheck source fingerprints and byte lengths.
3. Reject unsupported encryption and unresolved blocking warnings.
4. Confirm the user acknowledged signature invalidation where applicable.
5. Validate snapshot invariants and resource limits.
6. Load sources through the export adapter.
7. Construct output pages in document order from source references.
8. Apply supported form values.
9. Apply edit objects in explicit z-order using canonical-to-PDF transforms.
10. Embed deduplicated assets and approved fonts.
11. Save generated bytes.
12. Compute generated metadata needed for validation.
13. Send generated bytes to a fresh validator.
14. Enable download only after validation passes.

Ordering within each page is deterministic. Identical source bytes, snapshot, adapter version, and export options should produce semantically equivalent output. Byte-for-byte identity is preferred but not required if libraries inject nondeterministic metadata; any such behavior must be documented and normalized where safe.

All Version 1 edit objects are exported above the original page content and supported form appearances. Within that overlay layer, `objectOrderByPage` is authoritative from back to front. Whiteout is an opaque drawing operation, not deletion or redaction; the interface and exported metadata must not call it secure redaction.

## 20. Validation pipeline

Per-export browser validation:

- Output is non-empty and below the maximum generated size.
- Fresh PDF.js instance parses the generated bytes.
- Page count matches the snapshot.
- Page dimensions and rotations match expected geometry.
- Every changed page completes a low-scale render.
- Supported form values are read back where APIs permit.
- Validation is time- and resource-bounded.

Controlled corpus in CI additionally:

- Runs QPDF structural checks.
- Reopens and renders in supported browser engines.
- Verifies expected page mapping and geometry.
- Compares edit placement within the approved tolerance.

Validation failure:

- Blocks the generated download.
- Preserves original bytes, edit state, and recovery.
- Returns a stable, private error code.
- Offers retry only when safe.
- Never substitutes a rasterized or partially generated document silently.

## 21. Recovery architecture

### 21.1 Checkpoint contents

```ts
interface RecoveryCheckpoint {
  schemaVersion: number;
  documentId: DocumentId;
  documentRevision: number;
  createdAt: string;
  expiresAt: string;
  sourceManifest: RecoverySourceEntry[];
  assetManifest: RecoveryAssetEntry[];
  documentState: EditorDocument;
  checksum: string;
}
```

History persistence is optional and separately versioned. The minimum recovery promise is the latest committed document state, not the complete undo stack.

### 21.2 Commit strategy

1. Debounce after committed transactions.
2. Confirm storage estimate and policy.
3. Write missing source/asset blobs using content-addressed keys.
4. Write a new checkpoint record in one IndexedDB transaction.
5. Mark it current only after all references exist.
6. Garbage-collect unreferenced older records after success.

A failed save leaves the previous checkpoint intact and displays a non-blocking local-recovery warning.

### 21.3 Recovery rules

- Default expiry: seven days from the latest successful checkpoint.
- User can disable recovery and delete all local records.
- Opening private/incognito mode receives an honest persistence warning where detectable.
- Schema migrations are pure, version-by-version, and tested with fixtures.
- Unknown future schemas are not overwritten.
- Invalid checksums quarantine the checkpoint and preserve blobs until the user chooses deletion.
- Recovery is never described as cloud backup.

## 23. Security boundaries

Required invariants:

- The editor route has no third-party runtime scripts.
- All application, worker, font, CMap, ICC, and WASM resources are same-origin.
- PDF bytes enter through local file APIs and never through a URL supplied to PDF.js.
- PDF actions, embedded JavaScript, launch actions, and attachments are not executed.
- PDF links are displayed only through a controlled, user-initiated safe-link flow.
- Worker messages and persisted records are untrusted and runtime-validated.
- Blob/object URLs are scoped and revoked.
- The application is frame-protected and served with the approved CSP.
- No document-bearing data enters logs, URLs, headers, analytics, or crash reports.
- The source repository disposes bytes on explicit clear/close according to recovery choice.

## 24. State ownership and concurrency

Single ownership:

- Domain document: editor store
- Original/source blobs: source repository
- Asset blobs: asset repository
- Render cache: renderer infrastructure
- Recovery records: recovery store
- Command history: history service

Concurrency rules:

- Commands are serialized against a base revision.
- Stale commands are rejected or explicitly rebased by application logic; never silently applied.
- Render results carry page ID, document revision, geometry version, zoom, and render generation.
- Stale render results are discarded.
- Export uses a captured immutable revision.
- Closing a document cancels jobs, disposes render resources, and then releases in-memory sources.

## 26. Observability

Version 1 works without analytics.

If privacy-preserving telemetry is later enabled:

- It is metadata-only and documented.
- Event schemas use allowlists.
- No free-form strings from PDF libraries are accepted.
- No filename, digest, text, field value, signature, object content, or document identifier is sent.
- Development builds fail tests when forbidden fields appear.
- Users can disable telemetry.

Local diagnostic export may be offered later, but users must preview exactly what it contains before sharing it.

## 29. Approved decisions

1. Adopt the inward dependency layers and prohibit PDF library imports outside infrastructure adapters.
2. Store edit geometry in zoom-independent canonical page space measured in PDF points with a top-left origin.
3. Use explicit affine matrices for PDF, crop, rotation, viewport, and device transformations.
4. Represent documents as immutable source references, ordered page instances, edit objects, form values, and external asset blobs.
5. Use atomic domain transactions with reversible change sets and bounded history.
6. Separate document state from ephemeral interface state.
7. Use typed, runtime-validated worker protocols with explicit cancellation, revisions, and resource bounds.
8. Export only from immutable revision snapshots and validate with a fresh parser before download.
9. Keep recovery best-effort, transactional, schema-versioned, expiring after seven days, and user-deletable.
10. Adopt the error taxonomy and prohibit private document data in errors or telemetry.
11. Use the proposed test seams and require every future PDF engine to satisfy adapter contract tests.
12. Record material architectural changes through ADRs.
