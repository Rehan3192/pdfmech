# Technical Feasibility Report

Status: Approved  
Phase: 2 — Technical feasibility  
Working title: PDF Editor  
Research date: 2026-07-30
Approved by: Project owner  
Approval date: 2026-07-30

## 1. Phase goal

Determine whether the approved Version 1 product can be built as a privacy-first browser application, identify the technical and licensing constraints, select provisional technologies, and define the evidence required before production implementation.

This report authorizes a technical spike, not production architecture.

## 2. Executive conclusion

The approved Version 1 is feasible with important boundaries:

- Browser-local viewing, overlay editing, form filling, page organization, and export are feasible.
- Visual text replacement is feasible; general native editing of existing page text is not feasible with the proposed open-source stack.
- Standard encrypted PDFs cannot be safely edited with `pdf-lib` and must be rejected in Version 1.
- Existing cryptographic signatures cannot remain valid after ordinary document modification; users must be warned.
- Recovery storage is useful but cannot be guaranteed because browser quotas and eviction policies vary.
- A 100 MB or 500-page document must not be promised as smoothly editable until the technical spike validates it on reference devices.
- PDF.js is a credible rendering candidate.
- `pdf-lib` is a credible spike candidate for export, but its limitations and maintenance risk require an internal adapter and an exit strategy.
- MuPDF must not be embedded without satisfying AGPL obligations or purchasing a commercial license.

Recommendation: **conditional go** to the Phase 3 architecture and Phase 4 technical spike after the decisions in Section 15 are approved.

## 3. Proposed browser architecture

```text
Local file picker
       |
       v
Immutable original bytes ----------------------+
       |                                       |
       v                                       |
PDF.js worker -> rendered page canvases         |
       |                                       |
       v                                       |
Editor overlay -> domain edit commands          |
       |                                       |
       v                                       |
Export adapter + original bytes ----------------+
       |
       v
Generated bytes -> local validation -> download
```

The original bytes, editor state, and export implementation must remain separate. The interface must depend on our domain model rather than library-specific PDF objects.

## 4. Rendering engine assessment

### 4.1 PDF.js

PDF.js is the recommended provisional renderer.

Evidence:

- Mozilla describes PDF.js as a general-purpose, web-standards-based PDF parsing and rendering platform.
- It exposes a display layer suitable for rendering pages and retrieving document information.
- Its worker build permits parsing and rendering work away from the main interface thread.
- It uses the Apache 2.0 license.
- The official project shows active releases and ongoing maintenance.

Sources:

- [PDF.js repository and license](https://github.com/mozilla/pdf.js/)
- [PDF.js setup guidance](https://github.com/mozilla/pdf.js/wiki/Setup-pdf.js-in-a-website)
- [PDF.js official documentation](https://mozilla.github.io/pdf.js/getting_started/)

Constraints:

- PDF.js is primarily a parser and renderer, not a general PDF rewrite engine.
- Internal/core APIs are unstable and must not be used as our application contract.
- Rendering recovery for malformed files does not prove that exporting such files is safe.
- PDF.js version and worker version must be pinned together.

Decision: use only documented display-layer APIs behind a `PdfRenderer` adapter.

## 5. Export engine assessment

### 5.1 pdf-lib

`pdf-lib` is the recommended provisional export engine for the technical spike.

Supported capabilities relevant to Version 1 include:

- Loading unencrypted PDFs
- Drawing text, images, and vector graphics
- Embedding standard and custom fonts
- Creating and filling AcroForm fields
- Copying, inserting, removing, and rearranging pages
- Saving modified bytes in the browser

Sources:

- [pdf-lib official documentation](https://pdf-lib.js.org/)
- [pdf-lib repository, limitations, and encryption warning](https://github.com/Hopding/pdf-lib)
- [pdf-lib MIT license](https://github.com/Hopding/pdf-lib/blob/master/LICENSE.md)

Material limitations:

- It does not provide a supported API for editing existing non-form page text.
- It does not extract ordinary page text.
- It does not support encrypted documents. Its `ignoreEncryption` option does not decrypt a file and is explicitly unsafe for modification.
- It does not provide HTML/CSS layout or automatic word-processor-style text reflow.
- Advanced annotations and preservation behavior may require low-level PDF object manipulation, which we should avoid for the initial release.

Maintenance risk:

- A read-only npm registry check on 2026-07-30 reported `pdfjs-dist` 6.2.108, Apache-2.0, with registry metadata modified on 2026-07-28.
- The same check reported `pdf-lib` 1.17.1, MIT. Version 1.17.1 was published on 2021-11-06 and its registry metadata was last modified on 2022-05-12.
- `@pdf-lib/fontkit` 1.1.1 was reported as MIT with registry metadata last modified on 2022-04-06.
- The multi-year absence of a `pdf-lib` release is a material maintenance and supply-chain risk, not merely a slower cadence.
- Popularity does not remove abandonment, compatibility, or security risk.
- The Phase 4 spike must pin an exact version and test it rather than relying on unversioned CDN assets.

Decision: place all `pdf-lib` usage behind a `PdfExporter` adapter. Do not expose its classes in React components, editor state, commands, or persistence. Approval for the spike does not constitute approval for production; Phase 2 must record alternatives and Phase 4 must provide compatibility and output-preservation evidence before a production decision.

### 5.2 MuPDF

MuPDF is technically capable and has an official WebAssembly/JavaScript binding, but it is not approved for the initial product.

Reason:

- Artifex distributes MuPDF under AGPL and offers commercial licensing for embedding it in a product.
- AGPL obligations or commercial cost require a separate legal and business decision.

Sources:

- [MuPDF JavaScript documentation](https://mupdf.readthedocs.io/en/latest/guide/using-with-javascript.html)
- [MuPDF licensing notice](https://mupdf.com/releases)

Decision: retain only as a future evaluated alternative. Do not install or copy MuPDF code during the spike.

### 5.3 Commercial SDKs

Commercial PDF SDKs may solve more advanced editing problems but would weaken the goal of a low-cost, genuinely free core editor. They may also introduce license keys, domain restrictions, telemetry questions, or recurring costs.

Decision: do not adopt a commercial SDK in Version 1 without a documented build-versus-buy review.

### 5.4 Export alternatives and exit strategy

No evaluated alternative is a drop-in replacement for `pdf-lib`. The purpose of this comparison is to avoid mistaking a spike dependency for an irreversible product choice.

| Alternative | Strength | Barrier for this product | Disposition |
|---|---|---|---|
| Maintain a narrow `pdf-lib` fork | Preserves browser-local JavaScript model and MIT baseline | We inherit security, parser, compatibility, and maintenance responsibility | Contingency only after a scoped fork-cost review |
| QPDF compiled to WebAssembly | Mature structural transformations, encryption support, Apache-2.0 | No official browser product layer; editing overlays and forms still require substantial code; WASM build must be maintained and audited | Research fallback for structure/encryption, not initial spike |
| PDFium custom WebAssembly build | Widely exercised rendering engine with public embedder APIs | Large and complex C++/WASM toolchain; editing APIs do not directly supply our product; substantial update burden | Reject for Version 1; reconsider only with dedicated engine resources |
| MuPDF.js | Broad PDF manipulation and official JavaScript/WASM support | AGPL obligations or commercial license | Licensing decision required before use |
| Server-side PDF engine | Broad language and engine options | Violates default no-upload architecture and adds document custody | Reject for the free local editor |
| Commercial browser SDK | Faster access to advanced features and vendor support | Recurring cost, license restrictions, product dependence, privacy review | Separate future build-versus-buy decision |
| Build a PDF writer from scratch | Full control | Excessive correctness, security, standards, and maintenance risk | Reject |

Exit rule: if `pdf-lib` fails coordinate correctness, supported-fixture preservation, browser compatibility, or security review, the project pauses at the spike gate. We do not conceal the failure with rasterized exports or quietly introduce uploads. A new export-engine decision must be approved.

## 7. Coordinate-system feasibility

The largest correctness risk is mapping between:

- PDF user-space coordinates
- Page crop and media boxes
- Page rotation
- PDF.js viewport coordinates
- CSS pixels
- Device pixels
- Editor zoom

A simple `pdfY = pageHeight - screenY` formula is insufficient for all rotated and cropped pages.

Required approach:

1. Store edit geometry in normalized, unzoomed page coordinates owned by our domain model.
2. Use explicit affine transformation matrices between PDF space and viewport space.
3. Keep CSS display scale separate from device-pixel canvas scale.
4. Include page box and rotation in every transformation.
5. Round only at drawing boundaries, never in stored editor state.
6. Test forward and inverse transforms using portrait, landscape, 90/180/270-degree rotations, crop boxes, and mixed-size documents.

The spike must prove the one-PDF-point placement tolerance from the approved product specification.

## 8. Browser memory and performance

Browser processing avoids upload costs but moves memory pressure to the user's device.

Risk sources:

- Original bytes, parsed structures, rendered canvases, thumbnails, overlay state, and exported bytes can coexist.
- High-DPI canvases may use approximately four bytes per device pixel before browser overhead.
- Passing an `ArrayBuffer` to a worker without transferring it can duplicate memory.
- Rendering every page eagerly is not viable for large documents.
- A second complete output byte array may temporarily double document storage.

Required mitigations:

- Render only visible pages plus a small overscan window.
- Generate small thumbnails independently.
- Destroy page and canvas resources outside the active window.
- Use transferable buffers where ownership permits.
- Keep the immutable original in one authoritative owner.
- Run parsing, hashing, and export work in dedicated workers when library behavior allows.
- Limit simultaneous renders.
- Use abort signals or job generations to discard stale work.
- Detect memory or allocation failures and preserve the original.

The proposed 100 MB/500-page limit is a rejection ceiling, not a performance promise. The spike must define a lower recommended range if reference devices cannot meet the approved performance target.

### 8.1 Provisional reference-device tiers

Exact physical devices, operating-system versions, browser versions, and power settings must be recorded before measurements. The tiers below define minimum categories rather than claiming performance in advance.

| Tier | Provisional characteristics | Purpose |
|---|---|---|
| Minimum desktop | 4 logical CPU threads, 8 GB RAM, integrated graphics | Safe degradation and lower-bound usability |
| Reference desktop | 8 or more logical CPU threads, 16 GB RAM, modern integrated or entry GPU | Product-specification performance target |
| High desktop | 16 GB or more RAM and modern discrete/integrated GPU | Large-document observation, not the minimum |
| Reference mobile | Recent supported iOS and Android devices with at least 4 GB RAM | Fill, sign, and light annotation |

Tests must use physical Safari/WebKit hardware in addition to automated browser engines. Results from the developer's machine alone are not sufficient.

### 8.2 Provisional browser matrix

- Latest stable and previous major Chrome on Windows and macOS
- Latest stable and previous major Edge on Windows
- Latest stable and previous major Firefox on Windows and macOS
- Latest stable and previous major Safari on macOS
- Latest stable Safari on supported iOS
- Latest stable Chrome on supported Android

“Latest” is resolved and recorded on the date of each test run. Mobile is not required to meet full desktop layout-editing targets in Version 1, but its approved fill, sign, and annotation workflows must pass.

## 9. Local recovery and storage

IndexedDB can store significant structured data and blobs, but browser quotas differ and data may be evicted. MDN recommends handling `QuotaExceededError`; private browsing may provide only temporary storage. Browsers can estimate usage and quota, and sites can request persistent storage, but persistence is not guaranteed.

Sources:

- [IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)
- [Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- [Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API)

Decision:

- The active session works in memory.
- Recovery is a best-effort convenience, never the only copy.
- Check estimated capacity before storing the original.
- Handle quota failure without interrupting editing.
- Store an explicit schema version and migration policy.
- Expire recovery entries after seven days by default.
- Provide “Delete local recovery data” in the editor.
- Never claim that browser recovery is a permanent backup.
- Do not request persistent storage in Version 1 unless user research shows a clear benefit.

## 10. Security model

PDFs are untrusted binary input. Local processing improves confidentiality but does not eliminate parser, denial-of-service, supply-chain, or browser risks.

### 10.1 Required controls

- Serve exclusively over HTTPS.
- Pin dependency versions and commit the lockfile.
- Use automated dependency and license review.
- Self-host production scripts, workers, fonts, and WebAssembly assets.
- Do not load third-party scripts in the editor origin.
- Apply a restrictive Content Security Policy.
- Restrict workers with `worker-src 'self'`; avoid remote and data-URL workers.
- Do not use `eval`, `new Function`, or unsafe inline scripts.
- Do not execute JavaScript embedded in PDFs.
- Do not open embedded files or launch actions.
- Sanitize filenames before suggesting a download name.
- Revoke object URLs after use.
- Bound file size, page count, render dimensions, zoom, object count, path points, and history length.
- Catch parser and worker failures without exposing document data.
- Keep application logs metadata-only and allow analytics to be disabled.
- Maintain dependency update and emergency-disable procedures.

Web workers improve responsiveness but have their own execution context and network abilities. Worker code must be self-hosted and governed by an explicit CSP response header.

PDF.js must receive local `Uint8Array` data rather than a document URL. Its built-in resource URLs for CMaps, standard fonts, ICC profiles, and WebAssembly must be same-origin and self-hosted. XFA rendering remains disabled. Resource ceilings such as `maxImageSize` and canvas area must be set from spike evidence rather than left unlimited. Our custom interface will not wire PDF actions or embedded scripting into executable browser behavior.

Sources:

- [Using Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)
- [CSP `worker-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/worker-src)

### 10.2 Proposed production CSP baseline

The exact policy will be tested during production scaffolding. Initial intent:

```text
default-src 'self';
script-src 'self';
worker-src 'self';
style-src 'self';
img-src 'self' blob: data:;
font-src 'self';
connect-src 'self';
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
form-action 'self';
```

`connect-src 'self'` may later be reduced to `'none'` for the editor route if deployment and error reporting permit. Blob image access is needed for local previews; each use must be scoped and revoked.

## 11. Privacy verification

The “no upload” promise must be testable.

Required evidence:

- Automated browser test intercepts every request during open, edit, recovery, export, and clear workflows.
- Test fixtures include unique canary bytes, filename, text, and signature patterns.
- The test fails if any canary appears in a URL, header, body, log, analytics call, crash report, or service-worker request.
- Production contains no third-party script capable of reading editor memory.
- Browser developer tools documentation shows users how to verify the claim.
- Optional future cloud features use a visibly separate, explicit workflow and are not loaded into the local editor by default.

## 12. Export integrity and validation

Validation has two layers:

### 12.1 Per-export browser validation

Before download:

- Confirm non-empty output bytes.
- Reopen the generated bytes with a fresh PDF.js document instance.
- Confirm expected page count and dimensions.
- Render at least the changed pages at low scale.
- Confirm expected form-field and page-operation metadata where APIs permit.
- If validation fails, block the generated download and preserve the original plus edit state.

### 12.2 Test-suite validation

For every export fixture in automated testing:

- Perform the browser validation above.
- Run `qpdf --check` as an independent structural validator in CI.
- Render comparison pages in at least Chromium and Firefox.
- Verify expected page geometry, object placement, and form values.

QPDF is a PDF transformation and inspection tool with an Apache 2.0 license and is suitable for CI validation; it is not proposed as browser runtime code.

Sources:

- [QPDF documentation](https://qpdf.readthedocs.io/)
- [QPDF repository and license](https://github.com/qpdf/qpdf)

Correction to the approved product specification: two independent structural validators can cover the controlled test corpus, but running a native CI tool on every user's browser export is not feasible. Section 10 criterion 9 should be clarified during Phase 2 approval to distinguish per-export browser checks from release-corpus CI validation.

## 13. Dependency policy

Before any package is approved for production:

- Record name, exact version, source repository, license, purpose, and alternatives.
- Verify that the package comes from the expected publisher.
- Review release history, open security advisories, unresolved critical issues, and maintenance activity.
- Pin exact direct-dependency versions.
- Commit the lockfile and use deterministic installs in CI.
- Generate a software bill of materials for releases.
- Run vulnerability and license checks.
- Avoid runtime CDN dependencies.
- Place high-impact PDF dependencies behind internal adapters.
- Define a tested upgrade procedure and rollback path.

Dependency popularity alone is not approval evidence.

Registry observations are point-in-time evidence from 2026-07-30 and must be refreshed before installation.

## 14. Technical spike requirements

The disposable spike must answer these questions with recorded test results:

1. Can PDF.js render supported fixtures in isolated workers under the proposed CSP?
2. Can edit objects remain within one PDF point across zoom, rotation, crop, and mixed page sizes?
3. Can `pdf-lib` export text, whiteout, image, form, and page operations without damaging supported fixtures?
4. Which document features are lost or changed during save?
5. What memory and timing results occur for 20 MB/25-page, 50 MB/100-page, and boundary documents?
6. Can generated bytes reopen with PDF.js and pass `qpdf --check`?
7. Can all document data be proven absent from network traffic and logs?
8. What happens with encrypted, signed, malformed, XFA, and oversized fixtures?
9. Does IndexedDB recovery survive refresh and fail gracefully under quota denial?
10. Do the selected versions work in the agreed browser matrix?
11. Do PDF.js resource ceilings stop oversized images and canvases safely without breaking ordinary fixtures?
12. Can the custom viewer omit executable PDF actions while preserving safe links and supported annotations?

The spike is successful only if questions 1–7 pass. Questions 8–12 must produce documented, safe behavior and may justify revising provisional limits. Failure of coordinate correctness, export validity, or no-upload verification is a no-go for the proposed stack.

## 15. Approved decisions

1. Approve PDF.js as the provisional rendering engine, used only through documented APIs and an internal adapter.
2. Approve `pdf-lib` only as the provisional spike export engine, isolated behind an internal adapter.
3. Reject encrypted-PDF editing in Version 1 rather than using `ignoreEncryption`.
4. Reject native existing-text editing in Version 1; retain honest visual replacement.
5. Keep MuPDF and commercial SDKs out of the initial implementation pending separate licensing decisions.
6. Treat IndexedDB recovery as best-effort, with a seven-day expiry and clear deletion control.
7. Adopt the proposed CSP, self-hosting, worker isolation, dependency-pinning, and no-third-party-script principles.
8. Use fresh PDF.js reopening for every browser export and QPDF validation for the controlled CI corpus.
9. Clarify product-specification acceptance criterion 9 to reflect browser validation versus CI validation.
10. Proceed to architecture only after these decisions are approved; validate all provisional choices in the disposable spike before production scaffolding.
